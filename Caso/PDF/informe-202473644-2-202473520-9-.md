## Sección 4.1 Diseño del modelo documental
En la siguiente sección, se muestra cómo se diseña el modelo documental de SaludUSM para migrar la base de datos desde MySQL a MongoDB. Para realizar este diseño, primero es necesario entender qué es MongoDB y cómo organiza la información mediante documentos y colecciones.

MongoDB es una base de datos no relacional (NoSQL) basada en documentos. A diferencia de las bases de datos relacionales con las que se ha trabajado anteriormente, organiza la información mediante documentos agrupados en colecciones.

¿Qué son los documentos?

Los documentos son registros de una base de datos documental que permiten almacenar información sobre un objeto mediante pares campo-valor. En MongoDB, los documentos se almacenan internamente en formato BSON. Para este informe, se utilizará JSON para representar ejemplos de documentos y, posteriormente, para entregar las exportaciones solicitadas por el enunciado.
Un ejemplo de un documento representado en JSON, basado en un centro médico de **salud_usm**, es el siguiente:

    {

    "_id": 1,
    "nombre": "SaludUSM San Joaquín",
    "comuna": "San Joaquín",
    "region": "RM"
    }
En el ejemplo anterior, se observa que un documento cumple una función similar a una fila de una tabla relacional, ya que representa un registro con sus respectivos datos. Los documentos que representan entidades del mismo tipo, como los centros médicos, se pueden agrupar en una colección.

¿Qué son las colecciones?

Las colecciones son conjuntos de documentos y cumplen una función similar a las tablas de una base de datos relacional. En MongoDB, los documentos de una colección no están obligados a tener los mismos campos ni tipos de datos. Sin embargo, para SaludUSM se definirá una estructura común que permita organizar y consultar la información de manera consistente.

No todas las tablas del modelo relacional deben convertirse directamente en una colección. Esta decisión depende de cómo se consultará la información y de las relaciones entre los datos. Para diseñar las colecciones de **salud_usm**, se utilizará una descripción de sus campos y tipos de datos, como se muestra en el siguiente ejemplo de la colección Centros:
    Centros: {
        id: ObjectId,
        nombre: string,
        comuna: string,
        region: string
    }
Este formato se parece a la representación de un documento en JSON, pero se utiliza para describir su estructura. En lugar de mostrar valores concretos, indica el tipo de dato de cada campo y, al principio, señala el nombre de la colección.

Basándose en esta información y en el modelo normalizado de la Tarea 2, se proponen las siguientes colecciones para SaludUSM. Para definirlas, se consideran principalmente los datos necesarios para consultar el *Comprobante de Reserva de Hora* y la *Ficha de Atención*.

    Comprobantes: {
        cita: {
            id: Integer,
            fecha: Date,
            hora: Date,
            estado: {
                nombre: String
            },
            paciente: {
                rut: String,
                nombre: String,
                telefono: String,
                prevision: {
                    tipo: String
                }
            },
            medico: {
                nombre: String,
                especialidad: {
                    nombre: String
                }
            },
            centro: {
                id: Integer,
                nombre: String,
                comuna: String,
                region: String
            }
        }
    }

    Fichas: {
        cita: {
            id: Integer,
            fecha: Date,
            centro: {
                nombre: String
            },
            paciente: {
                rut: String,
                nombre: String,
                nacimiento: Date,
                sexo: String
            },
            medico: {
                rut: String,
                nombre: String,
                email: String,
                especialidad: {
                    nombre: String
                }
            },
            atencion: {
                id: Integer,
                motivo: String,
                observacion: String
                receta: Array
                diagnostico: {
                    codigo: String,
                    descripcion: String
                }
            }
        }
    }

    Citas: {
        id_cita: ObjectId,
        fecha: Date,
        hora: Date,
        estado_id: Integer,
        paciente_rut: String,
        medico_rut: String,
        especialidad_id: Integer,
        centro_id: Integer
    }

    Pacientes: {
        rut: String,
        nombre: String,
        telefono: String,
        nacimiento: Date,
        sexo: String,
        prevision_id: Integer
    }
    
    Medicos: {
        rut: String,
        nombre: String,
        email: String,
        centro_ids: Array
        especialidad_ids: Array
    }

    Centros: {
        id_centro: ObjectId,
        nombre: String,
        comuna: String,
        region: String,
        medicos_rut: Array
    }

    Estados: {
        id_estado: ObjectId,
        nombre: String
    }

    Previsiones: {
        id_prevision: ObjectId,
        tipo: String
    }

    Especialidades: {
        id_especialidad: ObjectId,
        nombre: String
    }

    Atenciones: {
        id_atencion: ObjectId,
        cita_id: Integer
        motivo: String,
        observacion: String,
        diagnosticos_id: Array,
        receta: {
            receta_id: ObjectId,
            medicamento: String,
            dosis: String,
            dias: Integer
        }
    }

    Diagnosticos: {
        codigo: String,
        descripcion: String
    }
Las estructuras anteriores servirán como base para construir los documentos de cada colección de **salud_usm**. Las colecciones propuestas no corresponden exactamente a todas las tablas obtenidas al normalizar las vistas hasta 3FN, ya que el modelo documental permite organizar los datos mediante documentos embebidos y referencias, según cómo se utilizará la información.

Para este caso, se mantienen previsión, especialidad y estado de cita como colecciones de catálogo, de acuerdo con lo solicitado en el enunciado. Los documentos que necesiten estos datos almacenarán sus identificadores como referencias. Al insertar o modificar información, se comprobará que dichos identificadores existan en los catálogos correspondientes.

Diagnósticos se mantiene como una colección independiente porque un mismo diagnóstico puede estar asociado a distintas atenciones. Cada atención almacenará un arreglo con los códigos de sus diagnósticos, mientras que sus descripciones se conservarán en la colección Diagnósticos.

Por otro lado, las recetas se almacenarán como un arreglo de documentos embebidos dentro de cada atención. Cada receta contendrá el medicamento, la dosis y los días de tratamiento. Esta decisión permite consultar las indicaciones entregadas junto con la atención a la que pertenecen.

También se propone almacenar Comprobantes y Fichas como colecciones que reúnen la información necesaria para presentar ambos documentos al usuario. Esta decisión permite consultar sus datos de forma conjunta, aunque implica repetir información presente en otras colecciones. Por ello, se deberá definir si estos documentos conservarán los datos del momento de su emisión o si se actualizarán cuando cambien los datos originales.

Las relaciones que en el modelo relacional se representaban mediante claves foráneas se expresarán mediante referencias entre documentos. Una referencia consiste en almacenar el identificador de otro documento. Por ejemplo, una cita contendrá el RUT del paciente y del médico, además de los identificadores del centro, la especialidad y el estado de la cita.

Estas referencias permiten identificar los documentos relacionados, pero no comprueban automáticamente que existan. Por ello, el código que inserte o modifique las citas deberá verificar que los datos referenciados sean válidos y que el médico pertenezca al centro y tenga asignada la especialidad indicada.

La relación entre pacientes y citas es de uno a muchos, porque un paciente puede tener varias citas y cada cita corresponde a un paciente. Se mantendrán ambas colecciones separadas y cada cita almacenará el RUT del paciente como referencia.

La relación entre citas y atenciones permite que una cita tenga ninguna o una atención, mientras que cada atención corresponde a una cita. Se mantendrán como colecciones separadas y cada atención almacenará el identificador de su cita. Se deberá impedir que una misma cita tenga más de una atención.

Las relaciones médico–especialidad y médico–centro son de muchos a muchos. Un médico puede tener varias especialidades y trabajar en varios centros, mientras que cada especialidad y cada centro pueden estar asociados a distintos médicos. Estas relaciones se representarán mediante los arreglos de identificadores incluidos en los documentos de los médicos.

La colección Centros también almacenará los RUT de sus médicos. Como esta relación estará representada tanto en Centros como en Médicos, cualquier cambio de asignación deberá actualizar ambos documentos para mantener la información consistente.

Este diseño establece cómo se organizarán los datos de SaludUSM en MongoDB y cómo se representarán sus relaciones. A partir de estas estructuras, se prepararán los documentos y se realizará la migración de los datos desde MySQL mediante Python.
